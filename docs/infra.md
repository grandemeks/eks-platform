## 8 Different layers

### Layer 1: Bootstrap: the things that outlive DEV environment

One small Terraform stack that's applied once that holds everything we don't want to destroy when we run `terraform destroy`

- **Route53 subdomain**, delegated from a zone we own - `incode-demo.grandemeks.tech`
- **ACM Certificate** for Route53 with validated DNS
- **ECR Repository** for images for go-appq
- **GitHub OIDC** provider for IAM roles that CI assumes

> I separated this the same way I did for my company when I built Azure Landing Zone, basically blast radius is smaller and for any mistakes that can be made. Certificate takes couple of minutes to validate and zone delegation is a manual step at the registrar. 
> 
> If these were in the same terraform state file as the cluster, every `terraform destroy` would throw them away and every rebuild would wait on DNS propagation.


### Layer 2: DEV Environment: VPC, EKS and RDS = network, cluster, database

This is my second Terraform stack, three modules with their own terraform state file.

**VPC - Network:** `10.0.0.0/16` across two AZs. 
Two public `/20`s carrying the ALB, two private `/20`s carrying nodes and RDS. 
One NAT gateway, not one per AZ: that's my cost trade-off I'll name before you do: 
it means one AZ's NAT failure takes out all egress, in Production I would set one per AZ.

**EKS:** Kubernetes Cluster on version 1.35. 
A managed node group of two `t3.large` on-demand instances in the private subnets. 
Two things worth meantioning are:

- **Access is managed with EKS access entries**, not the `aws-auth` ConfigMap. 
  Access entries are a real API, auditable, `terraform plan` shows a diff, and you can't lock yourself out by manually editing a ConfigMap.
- **Prefix delegation is on** for the VPC CNI. Without it a `t3.large` caps at 35 pods: three ENIs, eleven usable IPs each, plus two for host networking. My observability stack alone would have hit that, with prefix delegation it goes to 110.

**RDS - Database.** Postgres 18 on `db.t4g.micro`, single-AZ, 20 GB autoscaling to 50, KMS-encrypted with a customer-managed key. 
The master password is generated by RDS and stored in Secrets Manager with managed rotation. Terraform never sees the value and it's never in state as plaintext I put there. 
Reachable only from the cluster's security group; there's no public endpoint.

### Layer 3: The handoff: IRSA and Argo CD

Terraform creates four IAM roles for in-cluster workloads: the AWS Load Balancer Controller, external-dns, External Secrets, and Grafana's secret reader and then installs ArgoCD via Helm provider and passes those role ARNs down as service-account annotations.

**That's the entire interface between the two systems.** 
After this point Terraform doesn't touch the cluster's contents.

IRSA means the pod gets a **projected service-account token** mounted at a path in `AWS_WEB_IDENTITY_TOKEN_FILE`, with an audience of `sts.amazonaws.com`. The SDK calls `AssumeRoleWithWebIdentity` with that token. The role's trust policy conditions on the `sub` claim being exactly `system:serviceaccount:<namespace>:<name>`. So the identity is the service account, scoped per workload, not the node role shared by everything on the box.

### Layer 4: GitOps: the cluster reconciles itself

ArgoCD runs **app-of-apps**: one root Application pointing at a directory of Applications. 
Ordering is by **sync wave**, and the ordering is load-bearing, not cosmetic:

| Wave | What                                               | Why it must be here                                                                                                    |
| ---- | -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 0    | External Secrets, ALB Controller, external-dns     | they're the _enablers_ an `ExternalSecret` with no controller running just sits there, synced and inert, with no error |
| 1    | kube-prometheus-stack, Loki, Tempo, OTel Collector | the collector has to exist before anything emits, or the spans are simply lost                                         |
| 2    | the demo app                                       | needs its secret, its ingress, and its collector                                                                       |

Each infrastructure app is **multi-source**: the upstream Helm chart at a pinned version, plus this repo as a `$values` source so the values file lives in git next to everything else rather than being inlined in the Application.

Sync is `ServerSideApply` with `prune` and `selfHeal` on. If someone manually edits a workload, it automatically gets reverted.

### Layer 5: The request path, end to end

An HTTP request to the hostname:

1. **Route53**: the record was created by **external-dns**, watching the Ingress, not by Terraform
2. **ALB**: created by the **AWS Load Balancer Controller** from the Ingress, terminating TLS with the bootstrap ACM cert, using an **ingress group** so multiple Ingresses share one load balancer
3. **target group**: IP mode, targeting pod IPs directly, so there's no `kube-proxy` hop
4. **the pod**: a Go service: `/` does the work, `/healthz` is liveness, `/readyz` is readiness, `/metrics` is Prometheus

One detail worth mentioning: **liveness never touches the database.** 
If Postgres goes away, readiness fails and the pod leaves the load balancer rotation, but liveness keeps passing, so Kubernetes doesn't restart it. Restarting a pod doesn't fix a broken database; it just adds a CrashLoopBackOff to an existing incident. 
Same reasoning for migrations: a failed migration logs and continues in an unready state rather than exiting.

### Layer 6: Secrets

No secret value is ever in git or in a Helm value. 

The chain is:
**RDS generates it -> Secrets Manager holds it -> External Secrets reads it via IRSA -> writes a Kubernetes Secret -> the pod reads it as env.**

Grafana's admin password works the same way, generated by Terraform into Secrets Manager.

### Layer 7: Observability

Three signals, one place to look:

- **Metrics**: Prometheus scrapes the app's `/metrics` plus the whole cluster
- **Logs**: shipped to Loki, structured JSON
- **Traces**: the app exports OTLP to an **OpenTelemetry Collector running as a DaemonSet**, which forwards to Tempo. DaemonSet rather than a gateway so a single collector isn't a single point of failure for telemetry.

The part that makes it a platform rather than three dashboards is **the correlation**:

- **metric -> trace**, via exemplars: click a latency spike in a Prometheus panel and land on an actual slow request
- **log -> trace**, via a Grafana derived field that pulls `trace_id` out of the JSON log line
- **trace -> log**, back the other way from a span

Alerting is Prometheus rules into Alertmanager, routed by severity, with two null receivers standing in for PagerDuty and Slack. 
Every alert carries a `runbook_url` that resolves to a real section in docs/runbook.md.

### Layer 8: CI/CD

Three workflows, no long-lived AWS keys and **no cluster credentials in CI at all.**

- **`pr-checks`**: `terraform fmt`, `validate`, tflint, Trivy, Checkov, Helm lint
- **`environment`**: the Terraform apply/destroy, manually triggered
- **`app-release`**: builds the image, pushes to ECR, scans it with Trivy, **signs it with cosign keyless** (Fulcio issues a short-lived cert from the OIDC identity, Rekor records it in a transparency log so no signing key to store or rotate), then rewrites the image tag and digest in the Helm values file and commits.

That last step is the whole point: **the pipeline's final action is a git commit.** 
Argo CD notices and deploys. 
CI never holds a kubeconfig, so a compromised runner can't reach the cluster.
